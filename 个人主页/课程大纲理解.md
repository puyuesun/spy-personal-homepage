# 《项目制 Vibe Coding 入门模块》课程大纲 — 理解与拆解

> 本文件是对课程大纲 PDF（Vibe_Coding_课程大纲_中文.pdf）的阅读整理与理解，便于后续按阶段执行。
> 一句话主线：**把个人主页做成一个可发布、可反馈、可持续改进的真实产品。**

---

## 一、课程定位

- 这不是「做一次完美的网页」的课，而是一门**小型产品迭代课**。
- 核心能力不是写代码，而是：**用清晰的目标/受众/结构指挥 AI → 做出来 → 验证 → 发布 → 收集真实反馈 → 有依据地改进**。
- 每个课堂知识讲解不超过 60 分钟，其余时间用于独立制作、测试、向老师求指导。
- 评价看的是**最低任务是否完成、过程是否可解释、最终版本是否可用**，而不是功能数量、模型复杂度或工具品牌。

### 总评分结构（共 20%）

| 评分项 | 占比 | 核心判断 |
|---|---|---|
| 个人主页：阶段一至阶段四（V4） | 10% | 完成最低任务；有版本链、代表性证据、反馈驱动的改进 |
| 个人主页：期末扩展 | 5% | Digital Twin / 知识库连接 和/或 一个主要新功能 |
| 独立小作业 | 5% | 完成一个**非个人主页**的网站或小程序，并迁移迭代方法 |
| **合计** | **20%** | — |

---

## 二、四个阶段的推进逻辑

| 阶段 | 版本 | 要完成的变化 | 为什么这样做 |
|---|---|---|---|
| 阶段一 | V1 | 做出能看的个人主页，能本地预览 | 把想法变成可观察的产品 |
| 阶段二 | V2 | 根据自己的判断做多轮、小步打磨 | 把模糊审美变成可执行修改 |
| 阶段三 | V3 | 加入 Feedback 并公开发布到 GitHub | 让真实访问者可以使用和回应 |
| 阶段四 | V4 | 根据真实反馈做出有依据的改进 | 体验「听取用户—做决定—再测试」 |
| 期末扩展 | — | Digital Twin、个人知识库、项目库或主要新功能 | 把主页从展示页发展成个人产品 |
| 独立项目 | — | 制作一个非个人主页的网站或小程序 | 把方法迁移到新问题、新场景 |

**完成标准：每个阶段都有「最低任务」，完成最低任务即满足课程要求。额外加功能、用更复杂模型/工具不会自动加分。**

---

## 三、各阶段详细要求

### 阶段一｜先做出一个能看的版本（V1）

**目的：** 先让网页「存在并能被看见」。明确页面服务谁、展示什么、希望访问者做什么。

**要学到的：**
- 把个人主页当作最小可行版本（MVP），先完成核心信息，不一开始就追所有功能。
- 用清晰的目标、受众、页面结构指导 AI，而不是只说「做得好看」。
- 通过本地预览判断：内容是否真实、结构是否清楚、主要入口是否可用。

**最低成果：**

| 检查项 | 至少做到 |
|---|---|
| 可预览 | 网页能在本地打开并正常查看 |
| 内容真实 | 个人简介、经历、项目等核心内容可核验，不使用虚构信息 |
| 结构清楚 | 访问者能快速理解你是谁、做过什么、下一步可以做什么 |
| 第一版记录 | 保存 V1，并记录下一轮想改进的重点 |

---

### 阶段二｜用多轮打磨形成自己的版本（V2）

**目的：** 从「能看」走向「像自己的作品」。参考 GitHub 或公开设计，提炼适合自己的风格，多轮小修改形成 V2。

**要学到的：**
- 把问题说具体：指出现象、位置、影响，以及希望改变的方向。
- 一次只改一类问题，每轮后重新预览；避免一次大改后无法判断原因。
- 理解 Git / checkpoint：在重要节点保存版本，能回到可用状态并说明变化。
- 尊重开源许可，参考设计时保留必要的来源与许可信息。

**最低成果：**

| 检查项 | 至少做到 |
|---|---|
| 多轮迭代 | 完成若干轮有明确目的的修改，而不是只改一次颜色或文字 |
| 版本记录 | 保存 V1 与 V2，并能用一两句话说明每轮主要变化 |
| 代表性证据 | 保留有代表性的前后版本截图或链接 |
| 可用性 | V2 仍能正常打开，核心信息与导航没被改坏 |

---

### 阶段三｜加入 Feedback 并公开发布（V3）

**目的：** 让网页成为可被真实访问和回应的产品。访问者**无需登录**即可提交意见，你在 **Supabase Dashboard** 中查看反馈，并发布公开链接。

**要学到的：**
- 理解前端页面、后台数据、提交反馈之间的基本数据流。
- 设计简单明确的 Feedback 表单，收集有助于改进产品的信息。
- 完成公开发布，并从公开链接重新测试页面、表单、反馈流程。
- 建立基本隐私意识：不公开密钥，不收集不必要的敏感信息。

**最低成果：**

| 检查项 | 至少做到 |
|---|---|
| 公开链接 | V3 能通过公开链接访问（发布方式按课堂说明执行） |
| 可提交反馈 | 访问者无需登录即可提交，提交后有清晰提示 |
| 可查看反馈 | 你能在自己的 Supabase Dashboard 中看到提交内容 |
| 安全与隐私 | 前端不暴露 secret key；不收集敏感个人信息 |

**课后任务：** 邀请至少 **3 位不同类型**的人（亲人、同学、已工作的朋友或 HR 等）访问公开网站，收集 **3–5 条有意义、彼此不同**的反馈（可涉及内容、结构、使用体验或新需求）。

---

### 阶段四｜用真实反馈完成第一月版本（V4）

**目的：** 把反馈转化为产品决定，而不是「照单全改」。判断哪些问题值得优先处理，完成 V4，并验证修改没有破坏原有功能。

**要学到的：**
- 区分事实问题、个人偏好和新的需求。
- 对每条反馈做决定：采纳 / 部分采纳 / 暂缓 / 不采纳，并说明理由。
- 在公开版本上重新测试核心路径，确认反馈功能和页面仍然可用。
- 用简短复盘说明：用户说了什么、你改了什么、下一步还能做什么。

**第一月提交（主页部分，共 10%）：**

| 提交内容 | 要求 |
|---|---|
| V4 公开链接 | 能访问的最终第一月版本 |
| 版本链 | V1 → V2 → V3 → V4 的主要节点和变化说明 |
| 反馈证据 | ≥3 位不同类型反馈者、3–5 条有意义反馈；可提供代表性截图或记录 |
| 改进说明 | 反馈如何影响你的决定，以及修改后的验证结果 |

## 四、期末扩展与独立项目

### 主页扩展（5%）
在第一月版本基础上完成**一个有实质意义的扩展**，方向包括：
- **Digital Twin**：建立与自己相关的知识库并连接到主页，使回答更贴近真实的你。
- 本学期开始、进行或完成的**项目库**。
- **一个主要的新功能或产品能力**。
- 注意：仅改颜色、字体或少量文字**不算**主要扩展。

### 独立小作业（5%）
用同样的 Vibe Coding 方法，制作一个**不是个人主页**的网站或小程序。可自选主题、用户和技术工具，提交可访问版本及简短迭代说明。

---

## 五、评分与提交要求

- **过程证据（不需要完整聊天记录）**：保留足以说明过程的代表性证据，如若干次关键迭代的对话片段、前后版本截图、Git checkpoint 或版本说明、反馈记录。
- **AI 使用与学术诚信：**
  - 可使用自选的 AI 模型、代码工具和辅助服务。
  - 必须理解并检查最终内容：个人信息要真实，代码要测试，版本变化要能解释。
  - 不得抄袭他人作品、违反开源许可、伪造反馈或截图、冒用他人身份，或把密钥与隐私数据发布到公开仓库。
  - AI 生成内容若不准确或不适合公开，由本人负责修改、删除或说明。

---

## 六、我的关键理解（执行要点）

1. **产品思维 > 技术堆砌**：先问「服务谁、展示什么、希望访问者做什么」，再动手。
2. **版本链是硬要求**：V1→V4 的节点、截图、变化说明必须有，且每一步都能解释。
3. **反馈是核心素材**：至少 3 位不同类型的反馈者、3–5 条不同意义的反馈，并记录「反馈→决定→验证」。
4. **一次只改一类问题**：小步迭代，每轮可复现、可回退。
5. **安全底线**：前端绝不暴露 Supabase `service_role` / secret key；不收集敏感隐私。
6. **提交四句话**：先做出来，再逐步改；一次改一类问题；发布后认真听取反馈；每次提交都能解释自己的决定。
